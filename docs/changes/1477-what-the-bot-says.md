### 🐛 What the bot says after a short send, about `ANNOUNCE_TRANSFERS_EXCLUDE`, and to `unpause <old nick>` (#1477)

- **The "Not counted" line said bytes written, not bytes acknowledged.** A send the receiver closed early logged `[DCC-FAIL] ... having acknowledged 5,242,880 of 8,071,984 bytes. Not counted.` and then `[DB COUNTER] Not counted: ... ended short at 8071984 of 8071984 bytes.` The second line read `sent.bytes_sent`, what was handed to the socket, which is the whole file once the loop has written it. `start_dcc_send()` now passes `acked=acks.acked` into the `SentFile` it gives `record_completed_send()` (the field existed since #1336 and was left at its default there), and the line says `ended short: the receiver acknowledged 5,242,880 of 8,071,984 bytes`, with thousands separators like the `[DCC-FAIL]` line. `SentFile.acked` now defaults to None, not 0, and a `SentFile` with `acked=None` says the acknowledged count is not known rather than printing the written count or a 0; `finish_send()` counts None as nothing delivered in the transfer record, as 0 did. The "already held all ... bytes" line was checked and is unchanged: it states the file size, which is what the receiver held.
- **The `ANNOUNCE_TRANSFERS_EXCLUDE` help said "every channel".** The "sent" line only ever goes to the channel the file was asked for in, so an empty value now reads "Leave it empty to post it where the file was asked for." in `settings_help.py`, the `defaults.py` comment, `docs/INSTALL.md` and the Spanish and French dashboard help. `conf/settings.conf.sample` and the mIRC settings window block in `scripts/mirc/dccore.mrc` were regenerated (`gen_settings_sample.py`, `build_settings_window.py`). The wording is kept short on purpose: the mIRC window shows three lines of help and keeps whole sentences only, and a longer sentence ("...in whichever channel the file was asked for in.") would have been cut from it.
- **`unpause <old nick>` after a rename answered about the old nick.** A pause follows a rename (#1437), but `_cmd_unpause` only looked under the nick it was given, so the operator was told the old nick had nothing to lift while the pause stayed on the new one. `dcc.carry_send_fails()` now also records, under `failed_transfers_lock`, which nick a count was carried to (`runtime.send_fails_renamed`, `{old_key: (day, new_nick)}`, records from earlier days dropped as one is written; bound in `defaults.py` and kept across `!rehash` in `PRESERVE_RUNTIME`). `irc.note_nick_change()` passes the new nick as the server wrote it. `dcc.send_fails_renamed_to()` follows those records, a chain like `a -> b -> c` included, to the nick that holds today's count, stopping on a loop. When the named nick has no count of its own, the console lifts the pause on that nick and answers "`<old>` is now `<new>`: `<new>`'s N failed send(s) today are forgotten; its requests are taken again." The mIRC menu's "Unpause a nick..." sends the same console command; the dashboard has no unpause.
